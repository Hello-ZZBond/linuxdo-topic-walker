# linux.do 帖子巡览器（油猴脚本）

自动消费 linux.do 的 `/unseen` 未读列表：逐帖打开、逐屏滚动、读完自动跳下一个。用官方 JSON 接口判定帖子边界，断点续爬。

- 脚本：[linuxdo-topic-walker.user.js](./linuxdo-topic-walker.user.js)（由 `src/` 构建，见「代码结构」）

**只管未读。** 不提供「按 ID 扫描」模式——漫无目的地扫 topic id 会撞上大片已删 / 私密帖造成的空洞，纯属浪费额度。

## v3.0.0 修了什么

四个真实故障，全都是「真机跑过才暴露」的那种：

| 症状 | 根因 | 现在怎么做 |
|---|---|---|
| 已读评论永远是 0 | `collectFloors` 只认 `article[data-post-number]`；实测 linux.do 的楼层号只在 `id="post_N"` 上，那个属性根本不存在 | 多信号并集：`id="post_N"` 解析 ∪ `data-post-number`；解析不出来写日志告警，不再静默 0 |
| 点了赞但「已点赞」不动 | 按钮是 **discourse-reactions 插件**的 `btn-toggle-reaction-like`，`aria-pressed` 为 null，旧代码靠猜 class，判不出结果就记 `failed` | 点前后对比四信号（`aria-pressed` / class / title 含「取消」/ `.discourse-reactions-counter` 数值），任一变化即计 1；全不变记 `unknown` 并**仍然计 1** |
| 整页跳转模式暂停/停止无效 | 运行状态只存内存，每帖真跳一次页面 → JS 上下文重建、状态全丢，下一页无条件接力 | 状态落盘到 `sessionStorage`（`ldtw:run`），新页面先读回来再决定是否接力；停止后不再跳转 |
| 点停止后要等好几分钟 | iframe 兜底用 `(dwell + 屏数×每屏秒 + 60)` 秒的长 `setTimeout`，默认参数下 **243 秒**，期间完全不可中断 | 换成 200ms 步长的可中断等待，停止最多 200ms 退出；页面迟迟不渲染就告警，不假装读过 |

## 代码结构

源码按层拆在 `src/`，`node build.mjs` 按依赖顺序拼成单文件
[linuxdo-topic-walker.user.js](./linuxdo-topic-walker.user.js)。**改代码请改 `src/`，产物不要手改。**

| 文件 | 层 | 内容 |
|---|---|---|
| `src/constants.js` | 常量 | `NS` / 存储 key / `LIMIT` / `DEFAULTS` |
| `src/store.js` | 存储 | localStorage 读写 + `config` 默认值合并；业务层不直接碰存储 |
| `src/runtime.js` | 运行状态 | `rt` = 本页内存镜像；`run` = 落盘状态（整页跳转每帖重载页面，暂停/停止必须活过重载）；`hold()` 可被暂停/停止打断 |
| `src/view.js` | 视图 | 所有 DOM 写入集中在此，其他层只调用语义方法；日志缓冲 |
| `src/status.js` | 状态条 | 暂停按钮文案 + 状态徽标（页面重载后显示真实状态） |
| `src/http.js` | 网络 | 同源 fetch + 429 `Retry-After` 退避 + 网络异常重试 |
| `src/discourse.js` | 领域层 | `topic()` 探测、`listPage()` 分页、`toJsonPath()` 规整、`title()` / `floorCount()` |
| `src/visit.js` | 浏览计数 | `/pageview` + `?track_visit=true` 补发与确认头判定 |
| `src/scroll.js` | 滚动 | `floorOf` / `collectFloors`（多信号取楼层号）/ `stepwise` / `jumpToBottom` / `apply` |
| `src/frame-pane.js` | iframe 容器 | `open()` 全程可中断，且会等「楼层真的渲染出来」 |
| `src/session.js` | 会话统计 | 已读帖子 / 已读评论 / 已点赞 + 待补记清单（存 sessionStorage） |
| `src/liker.js` | 点赞 | 四信号判定 + 只点一次；成功后立即计数 |
| `src/readers.js` | 阅读器策略 | `iframe` / `goto` |
| `src/unseen-source.js` | 未读来源 | `prepare` / `peek` / `onMiss` / `advance` |
| `src/runner.js` | 编排器 | `runOnce` / `stopRun` |
| `src/panel.js` | 面板 | `FIELDS` 声明 + 渲染/回填/持久化 + 各类按钮动作 |
| `src/handoff.js` | 接力 | 整页跳转模式的落地页恢复 |
| `src/boot.js` | 启动 | 取回运行状态、建面板、触发接力 |

构建与验证（零依赖，Node 18+）：

```bash
node build.mjs            # 生成单文件 userscript
node build.mjs --check    # 只校验产物是否与 src 同步
node test/run.mjs         # 等价性回归：同一组场景分别跑基线产物与当前构建，逐项对比
```

两个接口是这套结构的核心：

```js
// 未读来源
{ prepare(), peek() → {id} | {done, reason}, onMiss(code), onHit(), advance() }

// 阅读器策略
read({ id, topic, title, cfg }) → {kind:'ok', read, pages} | {kind:'aborted'} | {kind:'handoff'}
```

`runOnce` 里没有任何 `if (mode === 'json')` 分支——阅读方式按 `cfg.mode` 从 `readers` 里取一个函数调用即可。想加一种浏览方式，多写一个 reader，主循环不用动。

面板同理：字段是一份 `FIELDS` 声明，渲染、回填、持久化全部由 schema 驱动。加一个参数只要往数组里加一行。

## 为什么用油猴而不是外部脚本

linux.do 挂在 Cloudflare 后面。任何脱离浏览器的裸请求都会拿到：

```
HTTP 403    Server: cloudflare    cf-mitigated: challenge
```

脚本跑在 linux.do 页面里，`fetch('/t/123.json')` 是**同源请求**，自动带上登录 Cookie 和 `cf_clearance`，CF 感知不到区别。

| 项 | 选择 | 原因 |
|---|---|---|
| `@grant` | `none` | 换成 `GM_xmlhttpRequest` 会脱离页面上下文，反而缺 Cookie 被拦 |
| 请求方式 | 原生 `fetch` | 同源，自动带凭证 |
| CSRF | 不需要 | 全是 GET |

## 未读列表怎么取

`https://linux.do/unseen` 只列你还没读过的帖子，id 全是有效的。

**这里有个必须绕开的陷阱**：读过的帖子会**立刻**从 `/unseen` 消失。如果边翻页边读，第 2 页的偏移就变了，会整批漏掉帖子。

所以分两阶段：

1. **收集快照**：连续取 `/unseen.json`，跟着 `more_topics_url` 翻页，直到它为空——全程不读任何帖子，列表保持稳定
2. **逐条消费**：从快照队列里取出 id 依次处理

`more_topics_url` 返回的是 `/unseen?page=1` 这种不带 `.json` 的地址，脚本会自动规整成 `/unseen.json?page=1`，确保拿到 JSON 而不是 HTML。

同一份快照内按 id 去重，跨页不会重复。浏览数据不落 localStorage —— 见「数据生命周期」。

## 怎么知道一个帖子读完了

`GET /t/{id}.json` 返回的 `highest_post_number` 就是楼层上界，**永远不用猜评论数**：

```js
const highest = meta.highest_post_number;        // 楼层上界
const maxPn   = posts.reduce((m, p) => Math.max(m, p.post_number), 0);
if (maxPn >= highest) break;                     // 读完 → 跳下一个帖子
```

两个必知的坑：

1. **`posts_count` ≠ 楼层数**。删帖后楼层号会跳号（…17, 19, 21…），`posts_count` 恒小于 `highest_post_number`。拿它算页数会翻到空页才停。
2. **`post_number` 是帖子内楼层号，不是评论 ID**。楼中楼（reply）不影响楼层序列。

## 两个指标，别混为一谈

L3 门槛同时要求两个东西，而它们由**完全不同的机制**记录：

| 指标 | 由什么记录 | 我们怎么保证 |
|---|---|---|
| **评论数 / 阅读时长**（`posts_read`、`time_read`） | 前端按楼层累计可见毫秒 → POST `/topics/timings` | iframe / 整页跳转里**逐屏滚动** |
| **话题浏览数**（`topics_entered`） | 列表页在**点击那一刻**代发的一次请求 | 每个帖子**单独补发**（见下节） |

关键事实：话题浏览数**不是**话题页加载时记的。所以用新标签打开话题、或者在 iframe 里加载，都不会涨 —— 这也是论坛上有人反馈「新标签打开后浏览话题数不达标」的根因。

**实测印证**：用本脚本的 iframe 模式跑过一轮后，评论数涨了、话题浏览数没涨，正好对应上面两个机制。

## 三种浏览模式

| 模式 | 行为 | 评论已读 | 话题浏览数 |
|---|---|---|---|
| `iframe 实读`（默认） | 右侧 iframe 内真实渲染，逐屏往下滚 | ✅ | 靠补发 |
| `整页跳转` | `location.href` 顺序跳，逐屏滚完再跳下一帖 | ✅ | 靠补发 |

v3.2.0 起移除了「JSON 速览」模式：它不渲染楼层、不产生 timings、也不补发浏览数，对「已读」和 L3 指标**完全没有作用**，属于无效功能。

打开帖子固定从**第 1 楼**开始，不做设定。

`整页跳转` 每帖都会真的重载页面，所以它的运行状态全部落在 `sessionStorage` 里：**暂停和停止能跨页面导航生效**，新页面先读状态再决定要不要继续。代价是每帖一次白屏。

「已读帖子」在 `整页跳转` 模式下由**落地页**结算（读完才 +1），交接时不会先记一笔 —— 那正是 v2 的虚增点。

## 滚动方式：为什么不能一步跳到底

Discourse 的阅读追踪按**「每个楼层在视口里累计可见的毫秒数」**计算。一步跳到最底，中间楼层的 `msecs` 接近 0，服务端不会标记已读——等于白跑一趟。

所以默认用「逐屏」：每次下移约 0.85 个视口高度，每屏停留 `每屏 s` 秒，到底后连续两次 `scrollHeight` 不再增长才收尾（Discourse 的下一批楼层是懒加载的）。

| 滚动 | 行为 | 适用 |
|---|---|---|
| `逐屏`（默认） | 一屏屏下移，每屏停留 | 想要真被记为已读 |
| `直接跳到底` | 一步到最底，只等懒加载 | 只求把帖子打开过，不求已读 |
| `不滚动` | 只加载首屏 | 只读首楼 |

两种实读模式都遵守这个设置：iframe 模式滚 iframe 内部，整页跳转模式滚当前页面本身。

代价是慢：一个 20 楼左右的帖子约需 8~10 屏 × `每屏 s`。按每屏 3 秒算，一篇约半分钟。

## 话题浏览数怎么补

「补记浏览数」开关打开时（默认开），每处理一个帖子会额外发一次请求：

1. **主路径**：`POST /pageview`，带 `Discourse-Present`、`Discourse-Track-View-Topic-Id`、`Discourse-Track-View-Session-Id`、`X-CSRF-Token` 等头部
2. **保底路径**：`GET /t/{id}.json?track_visit=true&forceLoad=true`（Discourse 核心参数）

判定靠响应头：`x-discourse-trackview` 或 `x-discourse-browserpageview` 为 `"1"` 才算服务器真的记上了。日志会直接告诉你结果：

```
👁️ /t/844796 浏览计数 ✅ 已确认 (pageview)
👁️ /t/844797 浏览计数 ⚠️ 已提交未确认
👁️ /t/844798 浏览计数 ❌ 未记上
```

确认状态只留在本次会话里（日志会当场写明）。面板上「👁️ 补记浏览数」会对本次会话所有**未确认**的帖子重发一遍，已确认的不会重复刷。

## 安装

1. Edge 装 Tampermonkey（或 Violentmonkey）
2. 打开 Tampermonkey 面板 → 添加新脚本 → 粘贴 `linuxdo-topic-walker.user.js` 全文 → 保存
3. 打开任意 `https://linux.do/` 页面，左下角出现面板

## 用法

1. 点「⏭ 单步」跑一篇，确认日志里出现 `📜 本轮读到 N 楼`、`浏览计数 ✅ 已确认`、右侧 iframe 也正常滚动
2. 再点「▶ 开始」

「▶ 开始」会重新收集一次未读快照；「⏭ 单步」复用已有队列，方便逐帖确认。队列剩余数显示在面板的「队列」计数上。

本次会话里没被确认记上的浏览计数，点「👁️ 补记浏览数」批量重发，不用重读帖子。

面板顶部的「状态」会显示 `空闲 / 运行中 / 已暂停 / 已停止`。点「⏸ 暂停」后当前屏立刻停住、不再开新帖，按钮变成「▶ 继续」；点「⏹ 停止」最多 200ms 退出，并且**不会再跳到下一帖**。两个状态都落在 `sessionStorage`，整页跳转模式重载后依然有效。

状态行下面还有一条**警示条**（黄 = 警告，红 = 错误），只在出问题时出现，写的是完整原因：

```
被限流（429）：队列还剩 3 帖，没有丢。等 1~2 分钟再点「▶ 开始」
收集未读列表失败：/unseen.json（HTTP 502）
已到「每帖最多屏」上限 60 屏：本页读了 1100 楼，剩余楼层未读，直接进下一帖
/t/844796 楼层没渲染出来（等了 6000ms），本页按 0 楼计
点赞失败：⚠️ 找不到点赞按钮（/t/844796）
```

点「▶ 开始」会清掉它；内容同时落盘（`ldtw:run` 的 `lastError`），整页跳转模式重载后仍能看到，不会一闪而过。

「▶ 开始」和「⏭ 单步」的区别：

| | ▶ 开始 | ⏭ 单步 |
|---|---|---|
| 未读快照 | **重新收集**（丢掉旧队列） | **复用当前队列**，不重取 `/unseen` |
| 跑多少 | 连续跑，直到队列清空才收工 | 只跑 **1 帖** 就停 |
| 会话计数 | **清零**（等于开一个新会话） | 保留，继续累加 |
| 适合 | 正式刷未读 | 先试跑一帖，确认参数、看日志对不对 |

队列跑空后就是**真的收工**：不会自己去重新收集、也不会再开一轮。想重来点「▶ 开始」；想让空队列重新取一次，点「🗑️ 清空队列」再开始。

「⏭ 单步」有两副面孔，和「▶ 继续」不冲突：

- **空闲时**：复用当前队列，跑 1 帖就收工（不重新收集 `/unseen`）
- **运行中 / 已暂停时**：像调试器一样只**放行当前这一帖**，跑完自动回到「已暂停」，等你再按一次

所以「继续」管的是**整轮闸门**（放着不管就一直跑到队列清空），「单步」管的是**一次放行一帖**。旧版本里运行中点「单步」是个静默空操作，v3.0.2 才让它有意义。

「🔍 自检」把当前页的关键事实一次性写进日志：楼层节点数、解析出多少楼层号、点赞按钮的 title / 图标 / 判定结果、本次会话计数与运行状态。选择器失配时先点它。

### 数据生命周期

**浏览数据只活一个会话**（一个标签页）：存在 `sessionStorage`，整页跳转、刷新都还在，关掉标签页就消失。`localStorage` 只放设置。

| 存储 | 放什么 |
|---|---|
| `localStorage` | 面板参数（模式、间隔、概率…）、折叠状态 |
| `sessionStorage` | 三个计数、未读队列快照、整页跳转的交接标记、待补记清单 |

所以不存在「历史记录无限膨胀」的问题 —— 配额和注意力都不用管它。

| 按钮 | 作用 |
|---|---|
| ♻️ 重置本次会话 | 三个计数 + 未读队列 + 待补记清单全部归零，等于手动开一个新会话 |
| 🗑️ 清空队列 | 只清未读快照，下次「▶ 开始」会重新收集 |

面板右上角两个按钮：

- **`–` 折叠**：只留标题栏。折叠状态会记住，刷新后保持
- **`×` 关闭**：面板消失，**不会再自己冒出来**（v2.3.2 修掉了每 2 秒轮询补建的旧逻辑，那会把关掉的面板复活）。想找回来按 `F5` 刷新页面

面板上的计数：

| 计数 | 含义 |
|---|---|
| 状态 | 空闲 / 运行中 / 已暂停 / 已停止 / 接力中 |
| 当前 | 正在处理的 topic id |
| 已读帖子 | 本次会话读完的帖子数（整页跳转模式由落地页结算） |
| 已读评论 | 本次会话真正滚动经过的楼层数（楼层号从 `id="post_N"` 解析，跨屏去重） |
| 已点赞 | 本次会话成功点赞的帖子数 |
| 队列 | 未读快照里还剩多少帖；停在中途会留着，下次「开始」自动重算 |

每次计数变化都会打一行日志，例如 `📊 +1 帖 / +12 楼 / +1 赞 → 已读帖子 3，已读评论 47，已点赞 2`。数字对不上时直接看这一行，能立刻定位是哪一步丢的。

## 参数一览

面板分三组：**帖子层面**按「一个帖子」生效，**评论层面**按「帖子内部的楼层」生效，**点赞**独立。三者的间隔互不复用。

### 帖子层面

| 参数 | 默认 | 作用 |
|---|---|---|
| 模式 | iframe 实读 | 怎么「打开」帖子。两种模式都会渲染楼层并计入评论已读 |
| 收集上限 | 500 | 一次最多从 `/unseen` 收多少帖。`0` = 不限 |
| 帖子间隔 ms | 1500 | **处理完一帖到开始下一帖之间等多久**。低于 1000 容易触发限流 |
| 补记浏览数 | 开 | 每帖额外补发一次浏览记录，让论坛「话题浏览数」增长。JSON 模式不生效 |

### 评论层面

| 参数 | 默认 | 作用 |
|---|---|---|
| 加载停留 s | 3 | 帖子加载完后先停这么久，让 Discourse 完成首屏楼层上报，再开始滚动 |
| 滚动 | 逐屏 | 逐屏才计入楼层已读；跳到底只求「打开过」 |
| 每屏停留 s | 3 | **滚一屏后停多久**。低于 2 秒大概率不计已读。**不影响「到底确认」** |
| 每帖最多屏 | 60 | 单帖滚动屏数上限，防止超长帖跑太久。`0` = 不限。**撞到上限会明确写日志**：`已到「每帖最多屏」上限 60 屏：读了 1100 楼就停，后面还有楼层没读` |

### 点赞

| 参数 | 默认 | 作用 |
|---|---|---|
| 给楼主点赞 | **关** | 给处理过的帖子点一个赞。已赞过的自动跳过，绝不会取消已有赞 |
| 点赞概率 % | 100 | 按百分比随机点赞：100 = 每帖都赞，0 = 都不赞 |
| 点赞最小间隔 ms | 3000 | 两次点赞之间至少隔多久，避免触发风控 |

> **帖子末尾为什么要额外等一会儿？**
> 滚动到底后要确认"真的没有新楼层了"，这段确认用的是**固定的 1 秒 × 2 次**，不跟随「每屏停留」。
> 尾段耗时 ≈ 2 秒（确认到底）+ `帖子间隔` + 下一帖的 iframe 加载时间。
> 按默认 `帖子间隔` 1500ms 算，约 4.5~5.5 秒才进入下一帖的正常滚动。

⚠️ **两个间隔别混用**：`帖子间隔` 管「帖与帖之间」，`每屏停留` 管「屏与屏之间」。

撞到 `429` 的处理链路：

1. 读 `Retry-After`（缺省按 10s，最少 3s）退避后重试
2. 同一个请求最多容忍 **2 次** 429；再失败就放弃这次请求，并让**整轮停下**
3. 停下时日志写 `⛔ 被限流打断：队列还剩 N 帖，没有丢`，状态行显示「被限流」，**不推进队列、不算已读**
4. 过 1~2 分钟再点「▶ 开始」即可接着跑

重点是「限流 ≠ 本轮跑完」：v3.0.3 之前这里会静默落到 `✅ 本轮结束`，让人以为队列已经刷干净了。

## 点赞

点赞**只给楼主帖（1 楼）**，而且**只走「点击页面真实按钮」**：

- linux.do 用的是 **discourse-reactions 插件**，按钮是 `button.btn-toggle-reaction-like`（`title="点赞此帖子"`，图标 `d-icon-d-unliked`），不是原生 `toggle-like`
- toggle 语义、CSRF、节流全部交给前端，我们不自己拼请求
- 点之前先判状态：已赞就跳过。**绝不会把你已有的赞取消掉**
- 只在 `iframe 实读` / `整页跳转` 模式生效（两者都会渲染楼层）

判定用四信号，点前点后各读一次：

| 信号 | 说明 |
|---|---|
| `title` / `aria-label` | 含「取消」= 已赞 |
| `class` | 含 `has-like` / `my-likes` / `liked` / `reacted` = 已赞 |
| 图标 | 含 `d-icon-d-unliked` 或 `#far-heart` = 未赞 |
| `.discourse-reactions-counter` | 点完计数 +1 也算赞成功 |

任一信号说已赞 → 跳过，一次都不点。四信号全说不清（`null`）→ **保守跳过并写日志**，宁可少一个赞也不误取消。点完四个信号都没变化 → 记 `unknown`，**仍计入已点赞**（点击确实发出去了，而我们绝不会点第二次）。

点赞**成功就立刻计数**，不等这一帖滚完 —— 否则整页跳转模式下「日志说已点赞、面板还是 0」会挂好几十秒。

点赞默认**关闭**，需要自己去面板勾上「给楼主点赞」。每帖多花约 2 秒（滚到 1 楼 → 点击 → 等状态回填）。日志会写明结果：

```
👍 /t/844796 楼主帖：👍 已点赞
👍 /t/844797 楼主帖：👍 早就赞过（跳过）
👍 /t/844798 楼主帖：⚠️ 找不到点赞按钮
👍 /t/844799 楼主帖：🤔 状态看不清，保守跳过（不敢点，怕取消已有赞）
```

找不到按钮通常是：没登录、帖子关闭了点赞、或插件又改了类名。这条链路只用 DOM 选择器兜底，**不做 API 猜测**。

## 实测：浏览计数多久才到账（2026-11）

用登录态在 linux.do 上跑的真实数据：

| 时间 | 浏览话题 | 浏览帖子 | 做了什么 |
|---|---|---|---|
| 04:53 | 722 | 25221 | 基线 |
| 04:56 | 722 | 25227 | 读完 1 条 5 楼 + 1 条 1 楼（+6 楼，立刻可见） |
| 04:58 | 722 | 25227 | 又等 2 分钟，仍未变 |
| **05:08** | **723** | **25232** | 同一批数据，延迟约 10 分钟后到账 |

结论：**楼层已读（浏览帖子）几乎实时；话题数（浏览话题）延迟 5~15 分钟**。判断脚本有没有生效，看「浏览帖子」和帖子的小蓝点，别盯着「浏览话题」的即时变化。

链路上的两个端点（同源 + Cookie）：

- `POST /pageview` —— **注意是 `/pageview`，不是 `/t/{id}/pageview`（后者 404）**；返回 204，端点存在但响应不带确认头
- `GET /t/{id}.json?track_visit=true` —— 返回 200，带 `x-discourse-trackview: 1` / `x-discourse-browserpageview: 1`

站点本身有个老问题：**在新标签页打开、或直接用链接进入话题，不记「浏览话题」**（社区帖：[t/3119902](https://linux.do/t/topic/3119902)、[t/2309449](https://linux.do/t/topic/2309449)）。补发就是为了绕开它。

## 验证情况

`node --check` 通过；`node test/run.mjs` 用 DOM stub 把**同一组 12 个场景**分别跑在
`test/fixtures/baseline.user.js`（v3.2.1 重构前产物）和当前 `src/` 构建上，日志、请求序列、
存储状态逐项深度相等；另有结构检查（面板字段 = `DEFAULTS`、阅读器策略、模块清单、产物不含测试钩子）。

测试台的假 DOM 按**实测抓到的真实结构**构造：楼层节点只有 `id="post_N"`（没有 `data-post-number`），点赞按钮是 discourse-reactions 那一套（`d-icon-d-unliked` + 计数器）。

**场景 A · 未读快照**
- 全部列表分页在**任何读帖请求之前**完成（防分页偏移错位）
- `more_topics_url` 的 `/unseen?page=1` 被正确规整成 `/unseen.json?page=1`
- 同一份快照内跨页去重，不重复读
- 队列消费干净后以「未读队列已清空」收工

**场景 B · 接口异常**
- 接口忽略 `?page` 时记录「未前进」并停翻页，不死循环
- 重复楼层不重复计数

**场景 C · iframe 逐屏滚动 + 浏览计数 + 点赞**
- scrollTop 分多屏递增，不是一步跳底
- 到底后连续两次 `scrollHeight` 不变即主动收尾，不撞 `最多屏` 上限
- **已读评论按 `id="post_N"` 解析，12 楼全部计上**
- 补发 **1 次** `POST /pageview`；主路径确认后**不再**走保底
- 未赞的帖：**只点 1 次**，点完必须是已赞态（不能把赞取消），「已点赞」+1
- **已赞过的帖：点击 0 次**，「已点赞」不增加，日志写「早就赞过」

**场景 D · 浏览计数保底**
- `/pageview` 被拒后自动落到 `GET ...?track_visit=true`，只发 1 次
- 经保底确认后不再进入「待补记」清单

**场景 E · 整页跳转交接**
- 交接时**不虚增**「已读帖子」（还没读，落地页才结算）
- `running` / `currentId` 正确落盘，队列已推进
- 跳转到 `/t/<id>/1`

**场景 G · 停止能跨页面重载**
- 上一页按过停止 → 本页**不接力**、不探测任何帖、不跳转
- 面板状态直接显示「已停止」

**场景 H · 暂停真的停住**
- 暂停 3.5 秒期间 `scrollTop` 一次都没变，状态行也不再前进
- 点「继续」后按钮文字还原，最终读完 12 楼

**场景 I · 队列跑空就收工（不重开一轮）**
- 落地页队列已空、但「本轮已收集」标记还在 → **不再请求 `/unseen`**
- 日志以「本轮未读队列已清空」收工
**场景 J · 暂停中单步**
- 暂停后「单步」只多跑 **1 帖**，跑完仍停在「已暂停」
- 点「继续」才接着往下跑


**场景 K · 429 限流**
- 同一个探测连续 3 次 429（首次 + 2 次重试）后放弃，不再空转
- 日志写「⛔ 被限流打断」，**队列保留**、已读计数不虚增
- 状态行显示「被限流」，而不是假装「本轮结束」

**场景 L · 撞屏数上限**
- 「每帖最多屏」= 2 时两帖都处理完（说明到上限就进下一帖，不会停在那里）
- 日志写明「已到「每帖最多屏」上限 2 屏：本页读了 12 楼，剩余楼层未读，直接进下一帖」
- 面板顶部出现对应的黄色告警条

**JSON 模式**
- 不发 `/pageview`、不走保底、不点赞

**面板守卫**
- 不注册任何轮询定时器；关掉的面板不会被复活

## 已验证 / 仍待确认

**已验证**（实测抓到真实 DOM 后修掉）
- 楼层号在 `id="post_N"` 上，`article[data-post-number]` 命中数为 **0** → v2「已读评论 = 0」的根因
- 点赞按钮是 discourse-reactions 的 `btn-toggle-reaction-like`，`aria-pressed` 恒为 null → v2 的 `isLiked` 只能靠 title 猜
- iframe 内渲染 + 逐屏滚动**确实**让「评论数」增长 → iframe 不会被当成后台标签
- 同一轮跑完后「话题浏览数」没有增长 → 证实它不由页面加载触发，必须补发

**仍待确认**
1. **`POST /pageview` 这套自定义头部在 linux.do 是否被接受**。看日志即可：显示 `✅ 已确认` 说明站方认了；一直是 `⚠️ 已提交未确认` 或 `❌ 未记上`，说明协议对不上，需要调整。
2. **`?page=N` 是否生效**。若不生效会打日志「未前进」并只读第一页，不会卡死。
3. **点赞按钮「已赞态」的真实 class / aria**。目前用四信号 +「拿不准就跳过」兜底；若日志长期出现「状态看不清」，点一次「🔍 自检」把按钮 HTML 发出来即可精确匹配。
